# Compiler Pipeline

This page walks through exactly what happens when you run `ocamlopt -mlir-backend foo.ml`, from the moment you press Enter to the moment an object file appears on disk.

## Invocation

```bash
ocamlopt -mlir-backend foo.ml -o foo
```

The `-mlir-backend` flag is defined in `driver/oxcaml_flags.ml` and handled in `driver/oxcaml_args.ml`. It tells the compiler driver to use the MLIR hook instead of the default Lambda pipeline.

## Phase 1: Parsing

**Files:** `parsing/lexer.mll`, `parsing/parser.mly`

The source file `foo.ml` is read by the lexer and parser. The parser is generated by Menhir from `parsing/parser.mly`. The output is a `Parsetree.implementation` — an untyped abstract syntax tree.

```ocaml
(* Parsetree fragment for: let x = 42 *)
Pstr_value (Nonrecursive,
  [{ pvb_pat = { ppat_desc = Ppat_var { txt = "x" } };
     pvb_expr = { pexp_desc = Pexp_constant (Pconst_integer ("42", None)) } }])
```

## Phase 2: Type inference

**Files:** `typing/typecore.ml`, `typing/typedecl.ml`, `typing/typemod.ml`

The type checker walks the `Parsetree` and produces a `Typedtree.implementation`. Every expression is annotated with its type. This is the last phase shared with the default backend.

```ocaml
(* Typedtree fragment for: let x = 42 *)
Tstr_value (Nonrecursive,
  [{ vb_pat = { pat_desc = Tpat_var (x_id, ...) };
     vb_expr = { exp_desc = Texp_constant (Const_int 42);
                 exp_type = int_type } }])
```

The `Typedtree` is the input to the MLIR backend. It contains enough information to emit code: types, primitive names, and the full structure of the program.

## Phase 3: Compiler hook

**Files:** `driver/optcompile.ml`, `backend/mlir/mlirize.ml`

In `optcompile.ml`, the `implementation` function calls `Compile_common.implementation` with a hook. When `-mlir-backend` is set, the hook `Compiler_hooks.Mlirize` is registered.

```ocaml
(* driver/optcompile.ml, simplified *)
let implementation ~start_from ~source_file ~output_prefix ~keep_symbol_tables =
  ...
  Compile_common.implementation
    ~hook_typed_tree:(Compiler_hooks.execute Compiler_hooks.Typed_tree)
    ...
```

`mlirize.ml` registers the actual hook:

```ocaml
(* backend/mlir/mlirize.ml *)
let () =
  Compiler_hooks.register Mlirize
    (fun (module_name, output_prefix, impl, ppf_dump) ->
      compile_from_typed ~module_name ~output_prefix ~ppf_dump impl)
```

This means: when the compiler reaches the `Typed_tree` hook, it calls `Mlir.compile_from_typed` instead of proceeding to the Lambda pipeline.

## Phase 4: Typedtree to custom MLIR

**Files:** `backend/mlir/translate.ml`, `backend/mlir/mlir.ml`

`translate.ml` walks the `Typedtree.implementation` and emits a custom MLIR module using the `ocaml` dialect.

It recognizes:

- **Constants** — `Texp_constant` (int, string) → `ocaml.int`, `ocaml.string`
- **Arithmetic** — `Texp_apply` with `%addint`, `%subint`, `%mulint`, `%divint`, `%addfloat`, etc. → `ocaml.binop`
- **Comparisons** — `%equal`, `%notequal`, `%lessthan`, `%lessequal`, `%greaterthan`, `%greaterequal`, `%eq`, `%noteq` on int/int32/int64/nativeint/bool/char/float → `ocaml.binop` with predicate
- **Let bindings** — `Texp_let` → SSA values in MLIR
- **If-then-else** — `Texp_ifthenelse` → `scf.if`
- **External calls** — `Texp_apply` with `external` declaration → `ocaml.extern_call` + `ocaml.extern`

Example emission for `let x = 4 + 3`:

```mlir
ocaml.module @Foo {
  ocaml.entry {
    %0 = ocaml.int 4 : !ocaml.int
    %1 = ocaml.int 3 : !ocaml.int
    %2 = ocaml.binop "+" %0, %1 : !ocaml.int, !ocaml.int -> !ocaml.int
  }
}
```

The `mlir.ml` module contains helper functions to create ops, map OCaml types to MLIR types, and handle the OCaml value representation (tagged integers, opaque values, strings).

### What it rejects

The translator currently emits clear error messages for unsupported constructs:

- Polymorphic / structural comparison on tuples, records, strings (needs `caml_equal` runtime call)
- Arbitrary `match` expressions (needs pattern compilation)
- `let rec` (needs fixpoint handling)
- Function literals as values (needs closure conversion)
- Non-external function calls (needs calling convention implementation)

## Phase 5: Lowering to standard MLIR

**Files:** `backend/mlir/lowering/lib/OcamlLowering.cpp`, `backend/mlir/lowering/lib/OcamlTypes.cpp`

The custom MLIR module is passed to `mlir-opt`, which runs the following passes in order:

```bash
mlir-opt \
  --convert-ocaml-to-arith \
  --convert-scf-to-cf \
  --convert-cf-to-llvm \
  --convert-arith-to-llvm \
  --convert-func-to-llvm \
  --reconcile-unrealized-casts \
  input.mlir > output.mlir
```

### `--convert-ocaml-to-arith`

This is the custom lowering pass written in C++. It lives in `backend/mlir/lowering/lib/OcamlLowering.cpp` and is registered as an `mlir-opt` plugin (`ocaml-mlir-opt`).

It lowers:

- `ocaml.entry` → `llvm.func` with name `caml<ModuleName>__entry`, returning `i64`
- `ocaml.int` → `arith.constant` (after shifting the tagged representation)
- `ocaml.binop` → `arith.addi`, `arith.muli`, `arith.cmpi`, etc.
- `ocaml.string` → `llvm.mlir.global` constant with the OCaml string header
- `ocaml.extern_call` → `llvm.call` with the declared C function signature
- `ocaml.extern` → `llvm.func` declaration

The lowering also inserts the runtime globals that the OCaml linker expects:

- `caml<Module>__gc_roots`
- `caml<Module>__data_begin`
- `caml<Module>__data_end`
- `caml<Module>__code_begin`
- `caml<Module>__code_end`
- `caml<Module>__frametable`

### Other passes

- `--convert-scf-to-cf` — lowers structured control flow (`scf.if`) to basic blocks (`cf.br`, `cf.cond_br`)
- `--convert-cf-to-llvm` — lowers control flow to LLVM dialect branches
- `--convert-arith-to-llvm` — lowers arithmetic to LLVM dialect instructions
- `--convert-func-to-llvm` — lowers function ops to LLVM dialect function ops
- `--reconcile-unrealized-casts` — removes any remaining `unrealized_conversion_cast` ops

After this pipeline, the module is entirely in the `llvm` dialect.

## Phase 6: LLVM IR emission

**Tool:** `mlir-translate` (external, from LLVM 22)

```bash
mlir-translate --mlir-to-llvmir output.mlir > output.ll
```

This produces a `.ll` file with standard LLVM IR. For the `4 + 3` example, the LLVM IR looks like:

```llvm
; ModuleID = 'LLVMDialectModule'
source_filename = "LLVMDialectModule"

@camlFoo__gc_roots = global i64 0
...

define i64 @camlFoo__entry() {
  ret i64 7
}
```

Note that the constant folding happens during lowering (the MLIR `arith` dialect does constant propagation), so `4 + 3` becomes `7` at compile time.

## Phase 7: Object file generation

**Tool:** `clang` (external)

```bash
clang -c -x ir output.ll -o foo.o
```

This produces a standard ELF/Mach-O object file that can be linked with the OCaml runtime and other object files.

## Phase 8: Linking (not yet implemented for MLIR backend)

In the current experimental state, the MLIR backend only produces `.o` files. Linking them into a full executable with the OCaml runtime is still work in progress. The in-tree tests verify correctness by compiling to object and then using a small C harness to call the entry function directly.

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   foo.ml    │ --> │  Parsing    │ --> │  Parsetree  │
└─────────────┘     └─────────────┘     └─────────────┘
                                              │
┌─────────────┐     ┌─────────────┐     ┌─────▼───────┐
│  Typedtree  │ <-- │  Typecheck  │ <-- │  Typedtree  │
│ (input to   │     └─────────────┘     └─────────────┘
│  MLIR backend) │
└──────┬──────┘
       │
       v
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  Custom MLIR │ --> │  mlir-opt   │ --> │ Standard    │
│  (ocaml dialect) │   │ (lowering)  │     │ MLIR (llvm dialect) │
└─────────────┘     └─────────────┘     └─────────────┘
                                              │
       v                                      v
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   foo.o     │ <-- │   clang -c  │ <-- │  LLVM IR    │
└─────────────┘     └─────────────┘     └─────────────┘
```

## Comparison with the default backend

| Step | Default backend | MLIR backend |
|---|---|---|
| Parse | Same | Same |
| Type | Same | Same |
| Hook | Lambda | Mlirize |
| IR | Lambda → Clambda → Cmm → CFG | Typedtree → MLIR → LLVM IR |
| Optimizer | Flambda 2 (optional) | MLIR passes (future) |
| Codegen | CFG → Assembly | LLVM IR → Object |
| Runtime | Full OCaml runtime | Partial (no GC yet) |
